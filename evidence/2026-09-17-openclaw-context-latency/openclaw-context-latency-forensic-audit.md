# OpenClaw context and latency forensic audit

**Mode:** retrospective, read only. **Window:** 2026-09-15 16:14:20 through 2026-09-17 16:14:20 UTC (17 September 18:14:20 Europe/Rome at the end). **Target interaction:** 2026-09-17 10:03 Europe/Rome = 08:03 UTC. **Evidence grade:** measured facts, derived calculations, supported inference, and unknowns are labelled below.

## Executive verdict

**CONFIRMED for token load:** accumulated conversation in one long-lived Cleo Telegram session dominated the 48-hour prompt volume. Its 646 model turns accounted for **202.9 million of 210.4 million derived prompt tokens (96.45%)**. The median in that session was 229,000 prompt tokens, compared with 15,000 in heartbeat turns. Recorded compaction count was zero in the analysed runs. A persisted reset boundary at 2026-09-17 05:55:53 UTC was followed by a median of 34,579 tokens across 12 turns, versus 231,373 across 634 earlier turns in the same session. The archive remained intact. This before/after association is strong evidence for session-history amplification, but not a controlled latency experiment.

**Latency verdict:** provider and model work, tool execution, and repeated model loops all contributed in the target interaction. Persisted data do **not** supply complete per-call provider completion spans or a full request-body byte count, so a numerical percentage attribution of total latency to provider versus OpenClaw preparation is **UNKNOWN**. In the target run, context compilation occurred about 1.86 seconds after the recorded run start; five model calls, five tool calls and model routing among three actual upstream models followed. The final response was recorded about 31 seconds after the target inbound Telegram event. Repeatedly sending large history is the established main *context/token* bottleneck, and a supported latency amplifier. It is not proven to be the main source of wall-clock seconds in every turn.

**Memory loss required for context optimisation: NO.** The observed reset boundary reduced model-visible history while the transcript stayed in SQLite. Daily memory, Vault and ClawMem can remain stored and retrievable. An eventual production change would need a tested continuity checkpoint and must retain retrieval access; none was made here.

The turn CSV is one row per assistant model output with persisted usage. `prompt_tokens_derived = input + cacheRead + cacheWrite`; these components are reported by OpenClaw/OpenRouter and their semantics can vary by upstream. It is a **derived prompt-load measure**, not a captured payload byte count or a reconstructed tokenizer result. `model_turn_interval_upper_bound_ms` is the elapsed time since the preceding transcript event and can include queueing, tools or preparation; it is **not** provider latency. Run duration and run tool count repeat on each model-turn row in that run. Historical context fields are blank/UNKNOWN unless a matching persisted report exists. The CSV uses SHA-256 prefixes of session/run IDs; raw message content is excluded.

Tool-schema size is separate from system-prompt size; do not add it inside 78,032. Largest single schema was `computer` at 4,057 chars. Current raw files at audit time: workspace `AGENTS.md` 18,140 decoded chars, `SOUL.md` 14,997, `IDENTITY.md` 609, `USER.md` 6,049, and `MEMORY.md` 24,243. `BOOTSTRAP.md` is absent. These file sizes **do not prove injection**. For the observed target run, the authoritative run report lists only the three workspace files above. It does not list workspace `USER.md`, workspace `MEMORY.md`, agent-directory copies or daily files as injected project context. Why those existing files were absent from this specific run report is **UNKNOWN** without a full retained prompt or hook trace. Current file sizes also differ slightly from the historical report, so current bytes must not be substituted for historical bytes.

The installed 2026.9.4 docs specify workspace bootstrap selection, per-file and total caps, and on-demand `memory_search`/`memory_get` for daily notes. They distinguish memory stored on disk from model context. Here, **stored but not shown in this run report** includes workspace `MEMORY.md`, 108 workspace `memory/*.md` files (about 772 KB), agent-workspace memory, ClawMem index and canonical Vault files. Explicit `clawmem_search` calls are **retrieval on demand**. The accumulated session conversation is **replayed model context until a reset boundary or pruning changes the active projection**. The `context-vault` and `clawmem` plugins are enabled, but historical bytes contributed by their hooks or implicit retrieval are **UNKNOWN**. There is no evidence that deleting stored memory is necessary.

## Optimisation candidates — proposals only

1. **Bound the active Telegram conversation with a continuity checkpoint and supported reset/compaction path.** Evidence: 202.9M tokens concentrated in one session and observed pre/post reset median change. Observed associated reduction: 231,373 to 34,579 median prompt tokens (**85%**); this is a historical association, not a predicted saving for every future turn. Expected latency effect is likely fewer prompt-ingest seconds and lower cache pressure, but unmeasured. Memory/continuity risk is **medium** unless active decisions, relationships and pending actions are preserved in a verified checkpoint and retrieval stays available. Reversible in principle because transcript is retained; installed 2026.9.4 supports reset boundaries, but production migration must be tested. Acceptance: same Telegram route, correct decisions/relationships on sample questions, old transcript retrievable, bounded prompt size, no side-effect replay. **Confidence: high for token reduction, medium for latency.**
2. **Review always-loaded AGENTS/SOUL and the 82-entry skill list for concise policy/skill metadata.** Evidence: 41.6k project-context and 17.9k skill-list characters in the target report. A specific safe reduction is **UNKNOWN** until paragraph/skill-level review; the full measured project-context ceiling is 41.6k chars, not an available saving. Expected latency effect modest relative to pre-reset historical history, potentially helpful on short turns. Memory risk **low** if information is moved to retrievable sources and behavioural tests pass; reversible through versioned files. Installed version has per-file/total bootstrap caps and skill-list reporting. Acceptance: compare `/context` report, required behavioural scenarios, and retrieval accuracy before/after. **Confidence: medium for fixed overhead, low for wall-clock benefit.**
3. **Review tool exposure for Cleo, starting with the `computer` schema, only if capability usage supports it.** Evidence: 10,332 tool-schema chars, 4,057 for `computer` in the target run. Maximum theoretical saving from all schemas is 10.3k chars, but removing all tools is neither intended nor safe; achievable saving is **UNKNOWN**. Expected latency effect small or unknown. Risk **medium** to operations; reversible config change on this version, but no change authorized here. Acceptance: compare tool-schema report and representative operational tasks. **Confidence: medium for fixed-token reduction, low for latency.**

## Risks, confidence and limits

The remote ledger repository is public, so this artifact set contains only counts, hashes, time, models, file names and narrow operational facts. Raw conversations, prompts, tool arguments, credentials and personal content remain on the VPS. The exact target question is located but not reproduced here. The source DB can change after the frozen extraction; rerunning the helper for the same window should preserve historical records barring maintenance. SQLite was opened in `mode=ro`; no OpenClaw config, memory, transcript, service or telemetry was changed.

Overall confidence: **HIGH** for the historical context/token concentration and reset association; **MEDIUM** for target run sequencing and fixed prompt composition; **LOW** for a numerical attribution of provider versus OpenClaw wall-clock latency. The rolling logs do not cover the first part of the window, provider response headers are not full completion spans, and OTel was not enabled/persisted for this period. `traceId`/`spanId` fields in ordinary logs do not constitute a complete exported OTel trace. Unknown historical composition fields remain blank/UNKNOWN in the CSV.
